# Chrome DevTools MCP

Default target: the Chrome DevTools team's [chrome-devtools-mcp](https://github.com/ChromeDevTools/chrome-devtools-mcp). Verify current Node/Chrome requirements, installed entrypoint and `--help` options before configuring.

1. Reuse a working server only if it is accessible to the target coding client and has an appropriate development-browser scope. Otherwise install a concrete package version outside the application dependencies.
2. Configure node + the installed MCP JS entrypoint with separate arguments. Prefer a dedicated isolated browser (`--isolated`) and `--headless` for unattended checks where supported. Do not automatically attach to the personal browser or expose a remote debugging port to the network.
3. Disable usage statistics and CrUX external lookups for the default setup using supported `--no-usage-statistics` and `--no-performance-crux` flags. Limit file access to the project using the supported workspace option; do not use unrestricted filesystem flags or disable the browser sandbox. Preserve a user's explicit alternative preference.
4. Verify real calls: open the actual preview URL, get the returned page ID, and inspect that page's console and network requests. An empty result from `about:blank` is not successful application verification. Report observed app errors without silently expanding an environment setup into app repair.

Future-agent guidance: use DevTools for console failures, failed requests and measured performance issues. Ordinary UI interaction verification can use Playwright; do not run duplicate browser checks without a reason. The tools use separate browser sessions, so login state and selected pages do not automatically carry over. Close only your own test pages/processes. A headless browser diagnosis is not a real-phone or microphone test.

## Official debugging Skills

During full setup, install or reuse the four official Skills `chrome-devtools`, `cookie-debugging`, `debug-optimize-lcp`, and `a11y-debugging`, in addition to the MCP server. These supply task-specific workflows for the same server, not a second MCP server. The `memory-leak-debugging`, `troubleshooting`, and `chrome-devtools-cli` Skills are optional when relevant; memory tools and CLI have additional prerequisites. Explicit user exclusions take precedence.

1. Inspect the actual server package version and locate its installed `skills/` directory, or obtain the Skills from the same official package release. Verify package version, skill names and their referenced files. If an existing server cannot be associated with matching upstream Skills, leave this layer pending or use a separately versioned compatible server and Skills; do not silently upgrade a shared installation.
2. Copy each complete skill directory, including referenced files, to the target Codex client's documented project or user Skill discovery location. Prefer project scope for a project-scoped server. Preserve existing custom or separately managed Skills: inspect provenance and compatibility, reuse compatible ones, and do not overwrite conflicting names. Back up any managed Skill before an authorized update, outside discovery paths. When the MCP server is deliberately updated, update its managed Skills from the matching package as a coordinated change. Do not duplicate Skills on repeat setup.
3. Verify all four `SKILL.md` files and their relative references, and confirm target-client discovery in a new session when observable. Record source package/version, scope and status for each. A file on disk is installation evidence, not proof the running client discovered or followed it; report pending discovery or behavior trials separately. Do not send a model request solely for verification unless authorized.
4. In the effective project tool guide, route browser debugging to `chrome-devtools`, authentication/cookie investigation to `cookie-debugging`, slow initial rendering to `debug-optimize-lcp`, and accessibility checks to `a11y-debugging` when relevant. Use the Skills selectively; installation adds guidance, not new MCP capabilities or guaranteed outcomes. Keep existing REA, Context7 and Playwright guidance.

Keep Vibe's browser isolation and permission boundaries when following upstream guidance. Do not automatically attach to personal Chrome or expose credentials from Cookie/Authorization headers, logs, screenshots or reports. Use a development session by default. Never change a client's read-only mode, approval rules or sandbox merely to make a tool available. Troubleshoot autonomously within authorization and leave authentication or explicitly required user actions pending. Check the installed tool's help and client discovery behavior rather than assuming options or a restart always work.
